## Resumen ejecutivo

KDD significa **Knowledge-Driven Development**. Es una metodología y plantilla
para trabajar con agentes de IA cuando no basta con que el agente produzca
algo que “parece correcto”. Su propuesta central es separar:

1. el conocimiento del proyecto;
2. la definición verificable de una tarea;
3. la implementación realizada por un agente;
4. la verificación determinista y la evidencia de que ocurrió.

KDD combina dos ideas:

- **OKF (Open Knowledge Format):** conocimiento, arquitectura, modelos de
  datos y contratos como nodos Markdown con frontmatter YAML y enlaces relativos.
- **CCDD (Contract-Driven Development):** cada tarea importante se define con
  un contrato que declara intención, target, firma, presupuesto, tests,
  perímetro y restricciones.

La diferencia importante frente a un `AGENTS.md` aislado o a una revisión hecha
por otro LLM es que KDD intenta que la decisión “pasa/no pasa” dependa de
comandos reproducibles: validadores, tests, hashes y comparación del diff.

## Qué ofrece

### 1. Base de conocimiento estructurada

`knowledge/` funciona como una pequeña base de conocimiento versionada.
Cada nodo debe tener `type`, `title`, `description` y `tags`; los nodos deben
estar enlazados desde `knowledge/index.md`. Los tipos reconocidos incluyen
`Concept`, `Data Model`, `Architecture` y `Task Contract`.

La regla más importante es no copiar una política o modelo dentro de cada
contrato: se enlaza el nodo fuente. Esto mantiene el contexto centralizado y
reduce contradicciones.

### 2. Contratos de tarea

Un contrato de `knowledge/contracts/*.md` define una unidad de trabajo:

- `task` e `intent`: qué se quiere conseguir;
- `target` y `signature`: qué artefacto o función se implementa;
- `test_command`: cómo se comprueba de verdad;
- `tests`: qué archivo contiene el oráculo;
- `tests_sha256`: hash del oráculo congelado;
- `touch_only`: perímetro de archivos permitidos;
- `budget`: límites declarativos de complejidad;
- `deps_allowed`: dependencias permitidas;
- `forbids`: capacidades prohibidas o declarativamente restringidas.

El contrato sigue el ciclo:

`draft → validated → implemented → verified`

El estado `verified` exige evidencia real de los comandos ejecutados; la
afirmación del agente por sí sola no cuenta.

### 3. Oráculos congelados

El test se escribe antes de la implementación y se sella con SHA-256. Si el
implementador cambia el test para hacer pasar una implementación incorrecta,
el hash deja de coincidir. Esto protege contra una de las fallas más comunes
del trabajo delegado: mover la meta en lugar de cumplirla.

El sello demuestra integridad, no calidad semántica. Por eso existe además
`scripts/audit_seals.py`, que detecta oráculos vacíos, sin asserts, sin
funciones de test o que no referencian al target.

### 4. Perímetro verificable

`touch_only` convierte “no modifiques otros archivos” en un dato que puede
compararse contra `git diff --name-only`. El gate de perímetro puede detectar:

- archivos modificados fuera del alcance;
- cambios al propio archivo de tests;
- targets que no están cubiertos por el patrón declarado.

### 5. Gates deterministas

El Nivel 1 está pensado para correr localmente y en CI, con Python puro en la
mayoría de los gates y sin evaluación por LLM. El repositorio declara 18 gates
de Nivel 1, más `validate_attestation` como diagnóstico local adicional.

Los gates cubren contratos, specs, OKF, ASCII de scripts, reglas declarativas,
skills, CHANGELOG, UX, diagramas, seguridad, compliance, privacidad,
accesibilidad, EOL de dependencias, observabilidad, cobertura, ejecución real
de `test_command` y secretos.

El Nivel 2 opcional usa `ccdd-complexity` por MCP para medir complejidad real,
firmas y límites de presupuesto con backends multi-lenguaje. Si no está
disponible, el Nivel 1 sigue siendo utilizable, pero el `budget` queda
declarativo y no se aplica con la misma fuerza.

### 6. Reglas de negocio como datos

`examples/rules/` y `scripts/rule_engine.py` introducen el concepto de
`rule contract`: reglas declarativas, golden sets sellados y reproducción por
un motor común. Esto permite validar políticas sin dispersarlas en ifs del
código y permite detectar deriva entre regla, golden y motor.

### 7. Capas de seguridad y calidad

La plantilla añade capas para hallazgos ya producidos por herramientas
especializadas: seguridad, licencias/compliance, privacidad, accesibilidad,
EOL, observabilidad y cobertura. KDD no pretende descubrir todos esos
hallazgos por sí mismo; valida que los artefactos estén bien formados, sellados
y cubiertos por reglas.

### 8. KDD-Board y MCP opcionales

`tools/kdd-board` ofrece un tablero visual con backlog, estados de agentes,
gates, runner de tests, explorador de contratos, puente WebMCP y un vault de
secretos ciegos. Es una interfaz opcional: el repositorio también funciona
solo con Git, Python y los scripts.

El vault no es una frontera de seguridad para código no confiable: oculta los
valores en listados y redacciones, pero el proceso de test que recibe el
secreto puede leerlo. La documentación lo reconoce explícitamente.

## Cómo se usa en la práctica

### Crear o adoptar un proyecto

```powershell
git clone https://github.com/MauricioPerera/KDD.git mi-proyecto
cd mi-proyecto
python scripts/init_project.py --name "Mi Proyecto"
python scripts/init_project.py --apply --name "Mi Proyecto"
```

El primer `init_project.py` es dry-run. `--apply` elimina únicamente el
manifiesto explícito de ejemplos, reescribe el índice de conocimiento y cambia
el H1 del README. No usa heurísticas para borrar archivos.

### Crear una tarea

1. Crear el test/oráculo primero.
2. Copiar `tests_sha256` con:
   `python scripts/validate_contracts.py --hash tests/test_mi_tarea.py`.
3. Crear el contrato desde `knowledge/contracts/TEMPLATE-task-contract.md`.
4. Declarar target, firma, test command, budget, tests, perímetro,
   dependencias y forbids.
5. Ejecutar `validate_contracts` antes de implementar.
6. Implementar solo dentro de `touch_only`.
7. Ejecutar el test real y los gates.
8. Registrar evidencia local en `.agents/logs/<task>-REPORT.md`.

### Validación mínima recomendada

```powershell
python scripts/validate_contracts.py knowledge/contracts
python scripts/validate_specs.py specs
python scripts/validate_okf.py knowledge
python scripts/validate_rules.py examples/rules
python scripts/validate_skills.py skills .agents/skills
python scripts/validate_changelog.py
python scripts/validate_test_commands.py knowledge/contracts .
python scripts/scan_secrets.py src
python -m unittest discover -s tests -p "test_*.py"
```

Antes de delegar, `python scripts/preflight.py --agent` ofrece un diagnóstico
consolidado de gates y recetas para los rule-id que fallen. No sustituye a la
ejecución de los gates ni convierte el diagnóstico en una nueva garantía.

## Flujo conceptual

```text
conocimiento OKF
      ↓
contrato + oráculo congelado + perímetro
      ↓
validación estructural
      ↓
implementación del agente
      ↓
test_command real + gates + diff
      ↓
evidencia reproducible
      ↓
verified
```

La metodología de ejecución añade capas de proyecto como definición,
planificación, delegación, rondas de auditoría y confirmación humana. La
garantía no está en que el agente “entienda” una instrucción larga, sino en
que no pueda cerrar la tarea sin dejar artefactos verificables.

### Fallo bloqueante encontrado y resuelto

En la auditoría inicial la suite completa no terminaba en verde en este entorno:

```text
Ran 774 tests in 135.247s
FAILED (failures=1, errors=2)
```

Los dos errores inmediatos son:

```text
ModuleNotFoundError: No module named 'src.sprint_admission'
ModuleNotFoundError: No module named 'src.sprint_planner'
```

La causa reproducible era que el repositorio contenía
`src/sprint_admission.py` y `src/sprint_planner.py`, pero no contiene
`src/__init__.py`. En este entorno Python resuelve `src` contra el paquete
global `C:\Python314\Lib\site-packages\src\__init__.py`, por lo que los
submódulos del checkout no se encuentran. Los tests aislados de sprint fallan
de la misma manera.

La corrección aplicada fue añadir `src/__init__.py`, convirtiendo `src` en un
paquete local inequívoco. También se corrigió el ejemplo de `budget` en
`knowledge/quickstart.md`, que usaba los nombres antiguos
`max_cyclomatic_complexity` y `max_nesting_depth` en lugar de
`cyclomatic_max` y `nesting_max`.

La verificación posterior produjo:

- tests aislados de sprint: 35 tests, `OK`;
- suite completa, primera corrida: 807 tests, `OK`;
- suite completa, segunda corrida: 807 tests, `OK`;
- `validate_test_commands`: todos los contratos en `PASS`;
- `preflight --agent`: `18/19`, con un único `SKIP` opcional para findings de
  seguridad ausentes;
- contratos, specs y OKF: todos en `PASS`.

También falla `test_gates_verdes_post_apply_en_copia` porque la copia creada
durante el test termina ejecutando la suite con esos mismos imports rotos.

### Hallazgo de diseño de adopción, parcialmente corregido

El quickstart afirmaba que una plantilla recién clonada debía terminar con la
suite completa en `OK`, pero el checkout inicial no lo cumplía en Python 3.14.
El problema de `src` ya está corregido y verificado en dos corridas. Queda como
mejora futura hacer que `init_project.py` ejecute una validación post-limpieza
de forma explícita, en vez de depender únicamente de su test de integración.

### Limitaciones honestamente documentadas por KDD

- El sello del test no demuestra que el test sea fuerte; solo demuestra que no
  cambió. `audit_seals.py` cubre debilidades mecánicas, no reemplaza mutation
  testing ni juicio humano.
- El budget de complejidad es informativo en Nivel 1. La aplicación estricta
  requiere Nivel 2/MCP.
- Macros y DSL embebidos pueden aparecer como árboles opacos para el parser
  de complejidad multi-lenguaje.
- `forbids` como `network`, `subprocess` y `llm` siguen siendo declarativos
  salvo verificadores específicos; el auditor lo informa.
- El vault de secretos no es aislamiento del código que ejecuta los tests.
- KDD aporta menos refinamiento conversacional que Spec Kit y menos
  orquestación de roles que BMAD; su ventaja está en la verificación
  determinista y el perímetro.

## Veredicto

KDD es una plantilla seria para gobernar trabajo de agentes en tareas donde un
resultado aparentemente correcto puede ser costoso o peligroso. Su núcleo
valioso es la combinación de conocimiento enlazado, contrato explícito,
oráculo congelado, perímetro verificable, ejecución real del test y evidencia.

No debe describirse como una garantía absoluta ni como un sustituto de revisión
humana. Debe describirse como una reducción mecánica y auditable de varias
clases concretas de fallo de agentes.

El repositorio está bien cubierto documentalmente y, después de la corrección,
los gates estructurales, los `test_command` y la suite completa quedan verdes.
El único estado no verificado es el artefacto opcional de findings de seguridad,
que no existe en el checkout y por eso aparece como `SKIP` en preflight.
